The 2 Sep pipeline stopped at step 1. `masters` built **136 contacts and held
283 vendors**, and the step-1 gate in `work/run_janapr.sh` refused to go on
because contacts are what every bill hangs off. Of the window's 11,256 bills,
**9,947 (88%) were blocked on a contact that had not been built**.

Backup of the file as it was: `post_sage_bills.py.before-unblock-20260903-095714`.

## 2. Four genuine bugs in the vendor mapping

### a. A PAN registration never sent its PAN  -  42 vendors, 144 bills
`registration_of()` recovers a PAN from LEGALNAME or BRN and returns
`("PAN", <pan>)`, but the payload only set `registrationNumber` under
`if reg_type == "GST"`. So every PAN vendor was posted with a registration type
and no number, and the platform answered **"Pan Can not be null"**. Now sent for
both. `profileType` is indexed at `GSTIN[5]` for a GSTIN and `PAN[3]` for a PAN -
the same entity-type character in the two formats; the old code read `[5]`
blindly, which on a bare PAN is a digit and silently profiled everyone `OTHERS`.

### b. Free-text `CODECTRY` made domestic vendors INTERNATIONAL  -  1 vendor
`OTHI058` holds country **"Mumbai"** against GSTIN `27XXXCX0003X1Z3`. The country
test ran before the GSTIN test, so it returned INTERNATIONAL and dropped both the
registration number and the state. A well-formed Indian GSTIN now settles it
first.

### c. A labelled BRN lost its GSTIN  -  7 vendors
`APVEN.BRN` is free text: `"GST - 29XXXPX0001X1ZN"`, `"29XXXP0021X X1ZV"`,
`"29 XXXH0022XX1ZI"`. `is_gstin()` is anchored, so these failed it and fell
through to the PAN branch - which read the PAN out of the very GSTIN it had just
failed to recognise. All 7 were being recorded as **PAN-only when Sage says they
are GST-registered**, losing their state with it. New `extract_gstin()` strips
whitespace and requires the exact 15-character pattern to still match. Nothing is
repaired: `"29XXXCX0002X12G"` is genuinely malformed and is still left alone.

### d. The shared-GSTIN reuse path could never succeed  -  26 vendors, 744 bills
"One GSTIN = one contact" is expected and handled: on *"Already exists with
registration Number"* the code looks the contact up and maps the Sage code onto
it. But it then demanded a billing address from
`GET /contact/address/{id}/CONTACT` - **a route that does not exist on this
build**. The OpenAPI spec (`/v3/api-docs`, 1,705 paths) offers only `POST` for
contact addresses; every read variant 404s. So `billing_address_for()` returned
None every time and all 26 fell through to the hold - while the address sat in
`yoda.address` all along.

The sibling that created the contact is already in the crosswalk carrying the
`addressId` its own create call returned, and one GSTIN is one contact, so that
*is* this vendor's address. The reuse branch now falls back to it. No API call,
no second address row. `SELD339` (392 bills), `SELD404` (222) and `SELD042` (67)
were the three biggest, and all three now reuse cleanly.

### e. A business refusal was retried six times  -  hours of wasted wall clock
`Api.call` retried any `>= 500`. But a 500 carrying an `errorMessage` is a
**refusal**, not a fault - "GST Info not available. Please add first.", "Pan Can
not be null" - and retrying costs 2+4+8+16+30+30 = **~90 s** to reach the same
answer. Measured: the first `masters` run of the day sat 15 minutes without
adding a contact, grinding through doomed retries. Now only a 500 the server had
nothing to say about is retried.

## 3. The CIN gate - the one that mattered

`ContactServiceImpl.getIsCinOrLlpinRequired` demands a corporate identifier
whenever the GSTIN's 6th character is `C` (company) or `F` (LLP). The platform
normally fetches it itself; on this devbox that lookup is dead -
`GET /contact/gst/{gstin}` answers **"GST Info not available. Please add first."**
and so does `POST /contact/`. Confirmed: before today, of the org's contacts the
GSTIN 6th characters present were only `P` (121), `L` (2) and `H` (1). **Not one
`C` or `F` had ever been created.**

This blocked **137 vendors carrying 8,773 of the 11,256 bills**.

**Where the identifiers came from.** Other organisations on this same devbox
already hold contacts for the same legal entities, with the CIN the platform's
own registry populated for them. A CIN belongs to the entity, i.e. to the PAN, so
matching is on the **PAN at GSTIN characters 3-12** - the box itself proves this
is right, carrying `U63011MH2006PTC162700` for DSV under both `06XXXCX0004X1Z3`
and `29XXXCX0004X1ZV`. `work/build_cin_map.py` writes `ref/cin_by_gstin.json`.

**Nothing is invented.** Where the box has no CIN, the vendor stays held. Where
it has more than one for the same PAN the script **refuses** rather than picks -
3 GSTINs, 4 vendors, 25 bills, including SGS INDIA which carries three different
CINs across other orgs.

Result: **77 GSTINs resolved, covering 100 vendors.**

Verified end to end: `FABI449` (QTEX CONSUMER PRODUCTS SERVICES INDIA, GSTIN 6th
char `C`) stored as `registrationType=GST`, `profileType=COMPANY`,
`corporateIdentificationNumber=U74999HR2019PTC077924` - the first company-type
contact in this org.

## 4. Two holds relaxed, on the user's explicit decision

### Pincode  -  64 vendors, 671 bills
Held because `address.pin_code` is `NOT NULL` and Sage holds `''` or junk
(`'58'`). Established first that **the pincode decides nothing here**:
`GET /address/pincode/{pin}` 404s on this build, so `pincode_state()` always
returns None, and the state we send is stored verbatim - the org already holds an
address filed `OTHER_COUNTRY` under a Chennai pincode. So a missing pincode now
falls back to the **head post office of the state the GSTIN has already proven**
(`STATE_HEAD_PINCODE`) and is flagged `pinCodeIsPlaceholder` in metaData. This
keeps a Tamil Nadu vendor in Tamil Nadu, unlike the old PowerShell loader which
defaulted everyone to the org's Karnataka 560059.

### State UNKNOWN  -  36 vendors, 352 bills
Resolved **only on corroboration**: the malformed BRN's leading two digits are
still a readable GST state code, and the pincode's postal circle is an
independent field. Where the two agree the state is evidenced twice and is not a
guess; where either is missing or they disagree the vendor is still held. Recorded
as `stateSource: "gstin-prefix+pincode"`. This resolves 3; the other 33 have
`CODESTTE = ''` and nothing to corroborate against, and `SELD078` is exactly the
case the rule is for - GSTIN says Karnataka, pincode says Delhi, so it stays held.

### The `2A7TX` mapping - answered, and it is SIX bills, not 136
**Correction.** The "136" came from group 2 of the 2 Sep `ERRORS-JanApr-2026.csv`,
which is a different and largely-resolved population. The live dry run's
`work/skipped.json` says **6**, which is exactly what RUNBOOK section 6 said all

What the line actually is, from Sage rather than from inference -
`FABI503/3103003994`:

    line 20  4E1M015      4800.00  @5%   tax 240.00
    line 40  4E2ME13-01   1585.50  @0%
    line 60  2A7TX03        79.00  @0%          <- no rate of its own
    4800.00 + 1585.50 + 79.00 + 240.00 = 6704.50 = AMTINVCHC

So it is an ordinary pass-through distribution the vendor charged, belonging on
a balance-sheet recoverable - precisely how `2A7TX04` is already treated. Most
documents net these to zero (the RCM +x/-x pair) and `classify()` skips them;
only where one nets non-zero is a ledger needed.

The org has no leaf for the domestic three: `GST Input` is a PARENT (`leaf = 0`)
so nothing can post to it, and every other child is rate-specific
(*SGST Input @ 2.50 %*) which these lines are not. The faithful mapping is one
leaf per Sage account, named from Sage's own `ACCTDESC`, `LIABILITIES`, parented
on `GST Input`, with `partyId` = org and `partyType` = `SELF` copied from the
existing GST leaves.

`work/make_passthru_ledgers.py` does exactly that and prints the `PASSTHRU_GL`
entries to paste back. **Dry-run verified; NOT applied** - creating
chart-of-accounts rows is an accounting change and wants a human yes. Worth
about Rs 6,903 across 6 bills.

### A defect this found: 570 items would have been refused mid-run

`product.hsnCode` is validated **"size must be between 2 and 8"**. Sage holds
**677 goods lines across 570 items** that break it - a trailing dot
(`60062200.`), a decimal tail (`60062200.00`) and full 10-digit ITC-HS codes
(`5208420090`). Every one would have been rejected individually, part-way
through a 17,000-product run.

New `normalise_hsn()`: drop everything after the first non-digit, then keep the
leading 8. HSN is hierarchical - 2, 4, 6, 8 - so the first 8 digits of an
ITC-HS code ARE the 8-digit HSN. `5407610000 -> 54076100`, woven polyester,
which is exactly what the item is.

Proven end to end on real Sage items through the loader's own `_item_payload()`:

    ID37742X-OTF1-022  Grey Blue MESH Pocketing  RAW_MATERIAL      YDS 1.21    hsn 54076100
    ID37742X-TH01-022  THRD Art# 8753 Tkt80      RAW_MATERIAL      BOX 244.82  hsn 54011000
    ID38447X-CB01      Carton 26*18*12           PACKAGING_ITEM    NOS 146.00  hsn 48191010
    MMCBBBTN0134       JUKI/SIRUBA BOBBIN        STORES_AND_SPARES NOS 6.00    hsn 84529099
    OTH-STN-0001       PEN                       CONSUMABLES       BOX 60.00   hsn 39261019

each with its own ITEM_PURCHASE ledger. All 20 probe products were deleted; they
sat in a `PROBE-*` namespace that cannot collide with the real
`SAGE-<item>-<unit>` scheme.
